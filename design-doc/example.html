Virtual Waitlist

Guests scan a QR code at the door, enter their name, phone, email and party size, and get a place in line. Hosts run the line from a live board. This page covers the guest flow, the host board, the data, the API, and the background jobs that send the texts.

Key decisions

Postgres holds the line

The order of the line and each party's status live in waitlist_entries. Celery never holds waitlist state, so a worker restart can't lose a guest's place.

Texts go through an outbox

A status change and its "send a text" event are written in one transaction. A relay hands the events to Celery. No text is lost or sent for a change that rolled back.

Live board without polling

Postgres NOTIFY fires on commit. Each API process listens once and pushes updates to the host boards over server-sent events.

Every row belongs to a restaurant

Every table and query is scoped by restaurant_id. Hosts only see restaurants they're members of. Settings like party size and grace period are per restaurant.

Architecture

The API's request path only touches Postgres. Everything slow or external (texts, emails, timers) happens after the commit, in the Celery worker. Updates for the board come from Postgres too, so every API process sees the same changes without a shared in-memory store.

  • Why the outbox: calling task.delay() from the endpoint would block the async event loop on a network call to Redis, and would lose the task if Redis was down or the process crashed between commit and publish. The relay keeps Celery out of the request path completely.
  • Why the SSE proxy: ADR 0001 keeps the browser from calling the API directly. A Next.js route handler forwards the event stream, so CORS stays off and the host's session cookie stays on the Next.js side.

Lifecycle of a waitlist entry

An entry moves through five statuses. The rules live in one pure function in waitlist/domain.py, so they're unit-tested without a database. Any move not drawn here raises InvalidTransitionError, a BusinessRuleError that returns 422.

A guest's position is calculated, never stored. It's the count of active entries that joined earlier, which the partial index answers quickly. Removing one party then changes nobody else's row.

API

All under /api/v1. Errors use the existing {"code", "detail"} shape from app/api/errors.py. New error codes subclass the categories in app/core/errors.py, so they need no handler changes.

Checked at the boundary

  • Name 1–80 characters, trimmed.
  • Phone parsed to E.164 with phonenumbers, using the restaurant's country as the default region.
  • Email through Pydantic's EmailStr.
  • Party size between 1 and the restaurant's max_party_size.
  • Host routes check staff membership for that restaurant_id, or raise PermissionDeniedError (403).

When a phone is already in line

The API returns 409 already_on_waitlist and re-texts the status link to that phone. It never returns the existing token in the response. Otherwise anyone who typed a stranger's number could take over their place and cancel it.

Background jobs (Celery)

Tasks are thin wrappers: open a session, call a service, commit. Business rules stay in the services, where they're already tested. Each task wraps the async service in asyncio.run and uses a NullPool engine created after the worker forks.

send_join_confirmationnotificationsoutbox: entry_joinedunique delivery row per event

expire_no_showwaitlistoutbox: entry_notified, delayed by the grace periodacts only if still notified with the same notified_at

purge_guest_piiwaitlistBeat, dailyclears name, phone and email on entries older than 30 days
  • Every task uses acks_late=True, exponential backoff with jitter (max 5 tries), and a hard time limit. Every provider call has its own timeout.
  • close_waitlists runs on a fixed interval and checks each restaurant's local time. That avoids one cron entry per restaurant and handles time-zone and daylight-saving changes.
  • Delayed tasks with a Redis broker get redelivered once they pass the broker's visibility_timeout, which is 1 hour by default. A 10-minute grace period is well inside that. The re-check covers any redelivery.
  • Run Beat as exactly one instance. The relay can run several copies safely because it claims rows with FOR UPDATE SKIP LOCKED.

Privacy and abuse

  • Phone and email never appear in logs or outbox payloads; tasks load them from the entry.
  • Phone numbers are masked on the board (···-0142).
  • Texts are sent only with sms_consent. STOP replies come in through the provider's webhook (a later phase).
  • Rate limits per IP and per phone on Join, stored in Redis.

Observability

  • A correlation ID goes from the request into the outbox payload and every task log line.
  • Metrics: active parties per restaurant, notify-to-seat time, no-show rate, text failure rate, age of the oldest unpublished outbox row.
  • Health: the relay and worker each expose a liveness check for their containers.

New code follows the structure of app/modules/menu/: router → service → repository, with the repository behind a Protocol.

Convention change

SqlMenuItemRepository.add commits inside the repository. The waitlist can't do that: the entry change and its outbox row must commit together. Waitlist repositories only add to the session, and WaitlistService commits once per use case. Move the menu module to the same rule in a small follow-up, so the codebase has one convention.

Plan

  1. Restaurants and the core waitlistTables, domain rules, guest join and status page, host board refreshing every 15s. Usable on day one, without texts.
  2. Outbox, Celery and notificationsRelay, worker, Beat, Redis in Compose. Confirmation and table-ready texts, no-show timer.
  3. Live boardLISTEN/NOTIFY, SSE stream and Next.js proxy. Polling stays as the fallback.
  4. ADRs0002-background-jobs (Celery + outbox) and 0003-waitlist-realtime (NOTIFY + SSE).

Shortcuts, on purpose

  • Static QR code. A photo of it lets someone join from home. Rate limits and one-place-per-phone limit the damage. Add rotating QR tokens if remote joins become a problem.
  • Guest status page polls every 15s. Move it to SSE if guest traffic makes polling expensive.
  • Wait estimate is parties ahead × avg_turn_minutes. Switch to a historical median once the reports module exists.

Open questions

  • Is email required, or only phone?
  • Max party size and grace period for each restaurant?
  • Host sign-in: there's no auth module yet, and the host board needs one.
  • Which SMS provider?

Tests

  • Unit tests for domain.py: every allowed transition, every rejected one, and the wait estimate.
  • Service tests with in-memory fakes, like tests/modules/menu/fakes.py: repeated idempotency key, phone already in line, stale version, and expire_no_show doing nothing after a seat.
  • Router tests through httpx for status codes and error codes.
